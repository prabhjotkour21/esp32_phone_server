ESP32 PHONE SERVER — PROJECT EXPLANATION
========================================
A beginner-friendly guide to every file, folder, and concept in this project.
Written so you can explain it clearly to your professor or team lead.

────────────────────────────────────────────────────────────────────────────────
1. BIG PICTURE — WHAT DOES THIS APP DO?
────────────────────────────────────────────────────────────────────────────────

Normally, when you think of a "server" you think of a computer in the cloud
(like AWS or a web hosting service). This app turns your *phone* into a tiny
local server that only works inside your home or office WiFi network.

Your ESP32 microcontroller (a small, cheap WiFi-capable chip) can connect to
the same WiFi and send HTTP requests — the same kind of requests a web browser
makes when you visit a website. This app listens for those requests and shows
the messages on screen.

No cloud, no internet, no external database. Everything runs locally.

2. FOLDER STRUCTURE — WHY EACH FOLDER EXISTS
────────────────────────────────────────────────────────────────────────────────

lib/
├── main.dart               ← App entry point. This is the first file Flutter
│                             runs. It sets up the theme and navigation.
│
├── models/                 ← "What does data look like?"
│   └── message_model.dart    A plain Dart class (no Flutter widgets here)
│                             that describes a single message: its text,
│                             when it arrived, and whether it came from a real
│                             ESP32 or was simulated.
│
├── services/               ← "How does the app talk to the outside world?"
│   ├── http_server_service.dart  Starts/stops the HTTP server, reads incoming
│   │                             requests, and calls back into the UI.
│   └── network_service.dart      Finds the phone's local IP address so we
│                                 know where to tell the ESP32 to connect.
│. 
├── screens/                ← "What does the user see?"
│   ├── dashboard_screen.dart     Main screen: server controls + message log.
│   └── wifi_config_screen.dart   Secondary screen: stores WiFi credentials
│                                 for reference.
│
└── widgets/                ← "Reusable visual pieces"
    └── status_card.dart          A small coloured card that shows whether the
                                  server is running or stopped.

PRINCIPLE: We separate concerns so that:
  • Models don't care about the UI.
  • Services don't care about how data is displayed.
  • Screens don't contain raw network code.
  • Widgets are dumb visual components with no business logic.

This makes the code easier to read, test, and change later.


────────────────────────────────────────────────────────────────────────────────
3. EACH FILE — WHAT IT DOES
────────────────────────────────────────────────────────────────────────────────

─── main.dart ───────────────────────────────────────────────────────────────

  • Calls runApp() to start Flutter.
  • Creates the MaterialApp with theme settings.
  • Contains _AppShell, a Scaffold with a BottomNavigationBar that switches
    between DashboardScreen and WiFiConfigScreen.
  • Uses IndexedStack so both screens stay alive (preserving state) when the
    user switches tabs. Without IndexedStack the server would stop every time
    the user visited WiFi Config.

─── models/message_model.dart ───────────────────────────────────────────────

  • Defines the MessageModel class with three fields:
      - text        → the actual message string
      - receivedAt  → a DateTime timestamp
      - source      → either "ESP32" or "Simulated"
  • Also provides a formattedTime getter that turns the DateTime into HH:MM:SS
    so the UI doesn't need to format it manually.
  • This is a "value object" — it holds data and nothing else.

─── services/network_service.dart ───────────────────────────────────────────

  HOW IP FETCHING WORKS:

  Every device on a WiFi network has a local IP address (e.g., 192.168.1.42).
  This IP is what the ESP32 uses to find the phone.

  Flutter's dart:io library exposes NetworkInterface.list(), which returns all
  network adapters on the device (WiFi, mobile data, Bluetooth, loopback).

  The code filters out:
    • Loopback addresses (127.0.0.1) — these are internal to the phone itself.
    • IPv6 addresses — the ESP32 Arduino library typically uses IPv4.

  The first remaining address is the WiFi IP. That's the address we display on
  the Dashboard and embed in the ESP32 quick-reference code snippet.

─── services/http_server_service.dart ───────────────────────────────────────

  HOW THE HTTP SERVER WORKS (step by step):

  Step 1 — Binding:
    HttpServer.bind(InternetAddress.anyIPv4, 3000)
    This tells the operating system: "Reserve port 3000 on ALL network
    interfaces." anyIPv4 means the server listens on WiFi, mobile data, USB
    tethering — anything that has an IPv4 address. Port 3000 is just a number
    we chose; it must match what the ESP32 sends to.

  Step 2 — Listening:
    _server!.listen((HttpRequest request) => _handleRequest(...))
    This starts an async loop. Every time a new TCP connection arrives and an
    HTTP request is parsed, the callback fires. The loop runs in the background
    without blocking the Flutter UI thread.

  Step 3 — Routing:
    _handleRequest checks request.method and request.uri.path:
      • POST /send-text  → calls _handleSendText
      • OPTIONS          → responds 200 (for CORS preflight)
      • anything else    → responds 404

  Step 4 — Reading the body:
    request.fold() collects all the incoming bytes into a List<int> and
    utf8.decode() converts them to a String. HTTP bodies arrive as a stream
    of byte chunks (especially for large payloads), so we must fold/await
    before we can read the full message.

  Step 5 — Calling back into the UI:
    Once we have the body text we create a MessageModel and call
    onMessageReceived(message). This is a function passed in by the Dashboard
    screen. The Dashboard's implementation of that function calls setState(),
    which triggers a UI rebuild.

  Step 6 — Responding:
    request.response.statusCode = 200; request.response.write("OK");
    The ESP32 receives this response so it knows the message was delivered.

  Step 7 — Stopping:
    _server.close(force: true) shuts down the server and releases port 3000.

─── screens/wifi_config_screen.dart ─────────────────────────────────────────

  • Provides two TextFormField widgets: one for the SSID (network name) and
    one for the password.
  • When the user taps Save, the values are stored in the widget's State object
    (_savedSsid, _savedPassword).
  • The screen then displays a code snippet showing how to use those values
    in an Arduino sketch.
  • NOTE: The app does NOT use these values to connect to WiFi. The phone
    is already on WiFi. These fields exist purely as a reference so the
    developer knows what credentials to hard-code in the ESP32 firmware.

─── screens/dashboard_screen.dart ───────────────────────────────────────────

  This is the most complex file. It owns all runtime state:

    _localIp        → the phone's IP, fetched on init
    _serverRunning  → whether the server is currently active
    _lastMessage    → the most recently received MessageModel (or null)
    _messageLog     → List of all messages, newest first
    _errorMessage   → displayed if server fails to start

  Key methods:
    initState()        → called once when the screen is created; fetches IP.
    dispose()          → called when the screen is destroyed; stops the server
                         to prevent port leaks.
    _startServer()     → calls _serverService.start(_onMessageReceived)
    _stopServer()      → calls _serverService.stop()
    _onMessageReceived → the CALLBACK given to the server service. When a
                         message arrives, this function runs setState() so
                         Flutter knows to repaint the UI.
    _simulateMessage() → creates a fake MessageModel and calls
                         _onMessageReceived directly, bypassing the server.
                         Useful for testing without hardware.

─── widgets/status_card.dart ────────────────────────────────────────────────

  A simple StatelessWidget that accepts a boolean (isRunning) and renders a
  coloured circle + text. Green = Running, Red = Stopped. A subtle glow is
  added when running to make it more visually distinct.

4. HOW STATE MANAGEMENT WORKS (setState only)
────────────────────────────────────────────────────────────────────────────────

Flutter redraws the screen when setState() is called inside a StatefulWidget.

Here is the exact flow when a message arrives from the ESP32:

  ESP32 sends HTTP POST
        ↓
  dart:io receives the TCP packet (background async)
        ↓
  HttpServerService._handleSendText() runs
        ↓
  Creates a MessageModel
        ↓
  Calls onMessageReceived(message)   ← this is a function pointer
        ↓
  DashboardScreen._onMessageReceived(message) runs
        ↓
  Calls setState(() { _lastMessage = message; _messageLog.insert(0, message); })
        ↓
  Flutter schedules a rebuild of DashboardScreen's widget tree
        ↓
  The UI updates — user sees the new message

No Provider, no Bloc, no streams (from the UI perspective). Just plain
function callbacks and setState.

Why is this enough?
  • There is only one screen that needs to react to messages.
  • The state is simple and local (no shared state across screens).
  • setState is the simplest, most transparent approach for a project this size.


────────────────────────────────────────────────────────────────────────────────
5. HOW THE UI IS CONNECTED TO BACKEND LOGIC
────────────────────────────────────────────────────────────────────────────────

"Backend" here means the HttpServerService (not a remote server).

The connection is made through a callback (function pointer):

  In DashboardScreen.initState (or _startServer):
    _serverService.start(_onMessageReceived);
                         ↑
                   this is a reference to the _DashboardScreenState method

  In HttpServerService.start:
    _server!.listen((request) => _handleRequest(request, onMessageReceived));
                                                         ↑
                                   stored and called later when request arrives

This pattern is called the "callback pattern" or "observer pattern" (simplified).
The service doesn't know anything about the UI — it just calls a function.
The UI doesn't know anything about TCP sockets — it just receives MessageModels.

The two sides are loosely coupled: you could replace the HTTP server with a
Bluetooth service or a USB serial service without changing the UI at all — as
long as it calls the same callback with a MessageModel.

6. HOW FUTURE ESP32 INTEGRATION WILL WORK
────────────────────────────────────────────────────────────────────────────────

From the app's perspective, nothing changes. The ESP32 just needs to:

  1. Connect to the same WiFi network as the phone.
  2. Find the phone's IP address (shown on the Dashboard — tap copy to
     clipboard and transfer it to the ESP32 firmware).
  3. Send an HTTP POST request:

       POST http://<PHONE_IP>:3000/send-text HTTP/1.1
       Content-Type: text/plain
       Content-Length: <length>

       <your message here>

  Arduino sketch example (ESP32 + Arduino framework):

       #include <WiFi.h>
       #include <HTTPClient.h>

       const char* ssid     = "YourNetwork";
       const char* password = "YourPassword";
       const char* serverUrl = "http://192.168.1.42:3000/send-text";

       void setup() {
         WiFi.begin(ssid, password);
         while (WiFi.status() != WL_CONNECTED) delay(500);
       }

       void loop() {
         if (WiFi.status() == WL_CONNECTED) {
           HTTPClient http;
           http.begin(serverUrl);
           http.addHeader("Content-Type", "text/plain");
           http.POST("Sensor reading: " + String(analogRead(34)));
           http.end();
         }
         delay(5000); // send every 5 seconds
       }

  The phone app receives this, creates a MessageModel, and updates the UI
  via setState — exactly the same path as a simulated message.

FUTURE IMPROVEMENTS (beyond this MVP):
  • Add a persistent notification so the server keeps running in the background.
  • Store messages in a local database (e.g. SQLite via sqflite).
  • Support JSON payloads so the ESP32 can send structured sensor data.
  • Add a graph widget to visualize numeric sensor values over time.
  • Support multiple ESP32 devices by tracking the sender's IP address.
